### Migration failure paths

Verified against a real v1 database generated by the Week 1–2 code (5 classes, 5 notes, 1 report, 3 batches, 1 pending preview):

- A fault injected mid-migration rolls the whole thing back; the database stays at version 1, no `users` or `_v1` tables remain, and a re-run then succeeds.
- A row-count mismatch aborts the transaction and the original data stays readable.
- A brand-new empty database builds v3 directly and writes no backup file.
- A database whose version exceeds what the program supports is refused at startup rather than silently altered.

### End-to-end check on a real server

A `werkzeug` server was started on a loopback port against a temporary database, driving the same `run.py` path a student uses:

`secret.key` generated → unauthenticated `/` redirected to sign-in → register (auto sign-in) → import CSV → preview → confirm → add a record under a new course → export and download the PDF (`%PDF-` header) → a second account requesting the first account's report id got 404 → logout blocked further access.
