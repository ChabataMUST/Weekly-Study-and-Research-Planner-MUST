小组：ChabataMUST（赵玥、王宇乐）

第3周按计划完成账号归属、课程/作业实体和数据迁移，是第4周要求修订历史和第6周资源检索的地基。33项自动化测试全部通过（原20项行为不变，新增13项），并在真实浏览器上走通了完整流程。

一、解决了原型里四个撑不住多用户的问题
1. source_key 原来是全表主键，两个账号导入同一份课表会冲突。现改为账号内唯一，课程的身份改用自增 id，改教室或时间不会断开已关联的记录。
2. 周报下载原来只按编号查，改一下网址数字就能拿到别人的周报。现在所有记录查询都带归属条件，访问他人记录返回"未找到"而不是"无权限"——后者会暴露该编号存在。这条正是验收场景 AC-01 和 NFR-S1 要测的。
3. 课表修订号原来是全库一个计数器，一个人导入会让另一个人的待确认预览失效。现改为每账号独立。
4. 备注的"课程/项目"原来是自由文本，做不出作业页、搜索无法按课程过滤、也没有稳定的父记录给修订历史挂靠。现改为真正的课程、研究项目和学术条目实体。

二、几个需要你知道的判断决策
· 旧数据处理：迁移时旧记录先归到一个不可登录的保留账号，你注册的第一个账号自动接管它。这样不必为单机场景做一套"认领旧数据"的界面。
· 迁移安全：迁移前自动备份 planner.sqlite3.pre-v3.bak，整个迁移在一个事务里，中途失败整体回滚。已用真实的第1、2周数据库验证过四条失败路径。
· 课表变更历史：按 Task2 6.2.8 要求建表并在确认导入时写入新旧值和确认时间，但界面留给第4周，避免下周再改一次表。
· 取消课程：数据库已有 state 字段，且重复导入不会把取消的课恢复；取消操作的界面留给第4周。
· 首页默认周从写死的 2026-09-28 改成当前这一周，样例周用日期选择器进入。

五、你怎么在本机验证
从 feature/account-ownership 分支拉取后，双击 setup.cmd 再双击 start.cmd，打开 http://127.0.0.1:5000 会看到登录页。注意不要和第1、2周的旧副本同时启动，两者都用5000端口，先启动的会占住端口导致新服务起不来（我今天就踩到了）。
跑测试：.venv\Scripts\python.exe -m pip install -r requirements-dev.txt，然后 .venv\Scripts\python.exe -m unittest discover -s tests -v，预期33项通过。
重点请 review 归属校验和迁移这两块：planner/auth.py、planner/db.py 的 _migrate_v1_to_v3，以及 planner/__init__.py 里各路由的 owner_id 过滤。第3周最容易出越权漏洞的就是这些地方。
